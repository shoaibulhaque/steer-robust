# Short playbooks

Read when a task benefits from a short recipe. Adapt the sequence; no mandatory phases or records.
Discover applicable project rules first; apply specialized guides when their subject matters.

## Investigate

1. Define the question and what observation would answer it.
2. Locate relevant docs, owners and execution paths; test competing explanations where practical.
3. Report the answer with sources and uncertainty. A cited investigation need not create code or a new tool.

## Fix a bug

1. Establish the trigger, broken behavior, owner and guarantees to preserve.
2. Reproduce or qualify the available evidence; trace the cause beyond the visible symptom.
3. Repair the responsible contract and add useful regression proof, including an important preservation case.
4. Run applicable checks, inspect the final diff and complete the authorized delivery.

## Build a feature

1. Clarify the user outcome, business rules and existing consumers.
2. Sketch realistic usage, data ownership and failure behavior; compare alternatives only when consequential.
3. Implement a coherent path with appropriate tests, project conventions and affected documentation.
4. Verify the actual contract and deliver within the requested scope.

## Refactor

1. Name the behavior and external contracts that must stay stable.
2. Identify the concrete structural problem; retain useful boundaries and necessary compatibility.
3. Change in verifiable units, migrating owned callers and removing obsolete task-related paths.
4. Check preserved behavior and inspect the diff for unintended semantic changes.

## Change stateful or concurrent work

1. Identify resource owners, authority, ordering and failure/crash points.
2. Define retries, unknown outcomes, capacity, cancellation and recovery at the affected boundaries.
3. Exercise relevant competing transitions and partial failures; verify cleanup and preserved safety.

## Upgrade or migrate

1. Determine requested versions, consumers, persisted data and actual rollout constraints.
2. Read relevant migration guidance; plan partial progress, mixed versions and rollback limits when applicable.
3. Update with repository tools, then verify compatibility, affected behavior and required metadata.

## Improve performance

1. Establish realistic sizes, dominant resources and a comparison metric.
2. Remove unnecessary or invariant work before adding caching or concurrency.
3. Compare equivalent behavior and report benefit, counter-costs and measurement limits.

## Review

1. Establish intent and project requirements; inspect the patch and relevant surrounding contracts.
2. Trace potential findings to reachable consequences, using only relevant evaluation lenses.
3. Report actionable defects separately from uncertainty and optional suggestions; no findings is acceptable.

## Explain or onboard

1. Establish the learner's goal and level; start with the product, users and problem it solves.
2. Define vocabulary, major components, owned data, business rules and a simple system picture before file detail.
   Use [existing docs and native navigation](efficiency.md#build-a-scoped-map) to ground the explanation.
3. Locate setup, architecture, contribution, testing and tool guidance; explain relevant rules and their reasons.
4. Trace one core journey through those components, its code and proof, including an important failure path.
5. Teach concepts through their role here; distinguish documented reasons, observed design and inferred tradeoffs.
6. Pause at useful boundaries for questions or a small exercise; do not equate reading with learner mastery.
7. Let the learner apply the next step when pairing. Retain brief progress and next steps if continued study needs them.

Understanding a system or one important flow can complete a learning session; contribution is not compulsory.

## Deliver and handle feedback

1. Inspect the final result against intent, applicable instructions, templates and required checks.
2. Summarize behavior, reason, evidence and material limits in the project's format.
3. Perform only authorized commit, publish, installation, PR, merge or messaging actions.
4. Verify the requested destination/revision; investigate feedback and follow authorized re-review requirements.
5. Clean up task-owned scratch resources directly. Preserve unrelated work and useful evidence.
